# 从现有流程到一站式工作台

## 原来的实际做法

1. 在旧手机打开开发者选项、USB 调试，连接电脑并授权。
2. 在搞机工具箱的 ADB 终端运行 `adb backup -all -shared -system -keyvalue -f file.adb`，手机确认备份。
3. 下载 `ab_decrypt`、准备 Python 环境和依赖，把备份解密/展开成 TAR。
4. 从 TAR 中完整解压或单独取出 `apps/com.android.providers.settings/k/com.android.providers.settings.data`。
5. 分别运行提取脚本与二维码脚本，得到表格、JSON 和二维码。
6. 把二维码复制到新手机，用系统扫码识别并保存网络。
7. 为减少重复操作，在手机连点器中录制“扫码 → 选择图片 → 返回 → 删除当前二维码副本”的循环。

Windows 还存在一条辅助路线：从电脑已保存网络导出表格，生成二维码，再与旧手机的结果对照。两份记录并不一定具有相同网络、密码或认证状态，不能仅按 SSID 覆盖合并。

## 哪些环节可以合并

| 原操作 | 当前工作台 |
| --- | --- |
| 分别找 ADB、输入备份命令 | 选择 ADB 和明确的设备；默认尝试定向备份，保留原全量模式 |
| 单独安装并运行解密脚本 | 直接输入加密备份，交互读取密码，在内存中处理 |
| 生成完整 TAR、解压全部应用 | 流式扫描，只保留目标设置文件，并校验流结束状态 |
| 多个脚本各写一套表格 | 统一格式，生成 JSON、CSV、二维码和校验摘要 |
| 图片名冲突、不知道哪些跳过 | 独立记录 ID；每条有输出状态与原因 |
| 手动寻找二维码输出 | 一键打开结果、离线扫码清单或复制到手机专用目录 |
| 不确定目标手机能否直接保存 | 先只读检测；明确写入后逐条记录命令确认和列表回读 |

“一站式”是同一工作台串联可用步骤。USB 调试授权、备份确认、系统扫码保存、厂商权限限制不会因为把界面放在一起而消失。

## 扫码路线保留什么

旧 ADB 备份可直接转换为 `wifi-password-manager.json`，无需经过 CSV 或扫码。该文件可携带认证类型、密钥、隐藏网络、自动加入、共享范围、计费覆盖和 MAC 随机化策略。已有 WiFi Password Manager JSON 中的备注也会随重新导出保留。目标机需要支持该 App 写入系统网络。

标准 WiFi 二维码用于传递名称、兼容的认证类型、密钥和隐藏标记。系统扫码器不会通过它恢复自动加入、计费、MAC 策略或备注。若要保留这些字段，请保留主数据及 App JSON。

这是不要求新机安装 Shizuku 的主要兜底路径。工作台可将生成的二维码复制到 `/sdcard/Pictures/WiFiMigrate/` 的独立批次目录，不碰手机其他照片。

使用连点器录制时，应只操作专用目录中的二维码副本，先用少量条目确认：

- 相册按文件名还是时间排序；删除当前副本后，下一次点击是否会选到下一张。
- 扫码后系统是否真正保存网络，尤其是网络不在附近的情况。
- 某些记录识别失败后，循环是否仍能回到正确界面。

本版本没有现成的全品牌录制文件，也不会自动删除手机二维码。原备份和主数据无需随扫码循环删除。电脑上的 `review.html` 提供另一种逐条展示方式，可以标记“已手动确认”，但不代替系统保存检测。

## 新增 ADB 路线为什么是可选的

目标系统声明 `cmd wifi add-network` 时，工作台可以准备保存计划。默认是预览；用户明确选择写入才执行。流程不调用 `adb root`，不恢复整机备份，也不以 `connect-network` 代替保存。

结果有三层：

1. `save_failed`：命令失败。
2. `save_acknowledged_unverified`：命令确认保存，但未能在列表中核对。
3. `saved_list_visible`：命令确认保存且名称/认证类型在列表中可见。

第三层仍未验证密码和联网。继续处理时，只有设备、记录指纹和列表状态都符合的条目才跳过；同名同类型而密钥不同的冲突记录要求人工选择，不自动覆盖决策。

## 后续优先级

第一优先是收集不同固件下的导出与保存实测，改进失败提示。之后可增加每批最多五条、由 Android 系统确认的导入 App，或为明确机型提供可复核的扫码适配。不会通过硬编码一个品牌的坐标来宣称全部手机兼容。
